02 / All eight stall categories

Definitions are paraphrased from Intel; examples and proposed tests are illustrative, not measured on a GPU. ISA snippets omit execution size, types and message descriptors.

01Instruction FetchInstruction availability

DOC VTune — Ponte Vecchio [1] [3]

Instruction delivery is pending.

DOC PTI — Arc B-Series [2]

XVE_STALL_INSTFETCH

At least one resident thread is waiting for instruction fetch while the XVE is stalled.

MODEL Example and mechanism

The next instruction has not arrived; instruction-cache misses are a possible cause, not the only proof.

Fetch → instruction buffer → thread readiness
Any instruction at a fetch boundary

INFERRED Optimization and diagnostic tests

Large unrolled loops or a large kernel footprint may increase fetch pressure.

Collect / inspect: Instruction cache L3 miss ratio (where available); code size; compare unroll factors. [6] [9]

UNKNOWN A fetch stall is not automatically an L1 instruction-cache miss.
02Dist or AccDependency

DOC VTune — Ponte Vecchio [1] [3]

A distance-based or architectural-register dependency is unresolved.

DOC PTI — Arc B-Series [2]

XVE_STALL_ALUWR

At least one thread is waiting for an ALU write to GRF/ACC while the XVE is stalled.

MODEL Example and mechanism

RegDist encodes instruction distance, not elapsed cycles. ACC is architectural accumulator state, distinct from GRF and from the explicit DPAS accumulation operand.

ALU producer → register dependency → consumer
add r10 r1 r2
mul r20 r10 r3 {F@1}

mul acc0 r1 r2
mac r20 r3 r4
GRF dependency
ADD writes r10 → MUL reads r10.
RegDist describes a prior instruction, not a delay in cycles.
ARF dependency
MUL writes acc0 → MAC implicitly reads accumulator.
It is not the previous instruction result by default.

Conceptual accumulator example; actual implicit accumulator selection and instruction support depend on ISA. DPAS uses an explicit accumulation input, not this implicit MAC operand.

INFERRED Optimization and diagnostic tests

Interleave independent softmax rows, shorten chains, or avoid unnecessary accumulator dependencies.

Collect / inspect: ALU activity; instruction-level sampling; inspect SWSB annotations; compare interleaved arithmetic. [6] [9]

UNKNOWN The combined metric cannot identify Dist versus Acc separately. F@1 is illustrative; valid encoding depends on the target.
03SBIDDependency

DOC VTune — Ponte Vecchio [1] [3]

A software-scoreboard dependency has not resolved.

DOC PTI — Arc B-Series [2]

XVE_STALL_SBID

At least one thread is waiting for a scoreboard token to become available while the XVE is stalled.

MODEL Example and mechanism

A token may track asynchronous source consumption, destination completion or reuse constraints. Memory is a common producer, not the only possible producer.

SEND issued → request outstanding → destination ready → consumer eligible
send r20 r10 ... {$0}
add r30 r31 r32
mul r40 r20 r41 {$0.dst}

Outstanding does not mean stalled

A request is outstanding once issued and before its relevant completion. Independent instructions can execute in that interval.

Hoist loads, double-buffer, interleave independent work; check source and destination hazards before register reuse.

Collect / inspect: ISA token producer/consumer analysis; bandwidth, cache metrics, XMX/ALU utilization; sweep independent work. [6] [9]

UNKNOWN SBID is not an exclusive memory-latency counter. Exact token behavior for DPAS varies by ISA.

XVE_STALL_BARRIER

At least one thread is waiting for Gateway to update Notify while the XVE is stalled.

MODEL Example and mechanism

Early-arriving hardware threads may wait for peers; slow memory or compute in one peer can cause synchronization delay in others.

INFERRED Optimization and diagnostic tests

Reduce redundant barriers, balance work, and inspect producer/consumer buffering. Never remove necessary synchronization.

Collect / inspect: Barrier count from ISA, subgroup timelines, per-workgroup timing, preceding memory dependencies. [6] [9]

UNKNOWN A barrier may also require memory ordering; total barrier region time is not necessarily pure synchronization stall.
05PipeResource / issue

DOC VTune — Ponte Vecchio [1] [3]

After arbitration an instruction cannot enter FP or extended math; GRF bank conflicts are an example.

DOC PTI — Arc B-Series [2]

XVE_STALL_PIPESTALL

A ready thread is held from scheduling; PTI lists GRF conflicts and SEND holds among examples.

MODEL Example and mechanism

Register-access constraints and execution resource holds are possible. The counter does not isolate a physical port or prove ALU saturation.

Ready instruction → arbitration → operand/dispatch hold
mad r20 r10 r11 r12

INFERRED Optimization and diagnostic tests

Test register allocation and operand layout, instruction mix, and occupancy; reduce avoidable pressure.

Collect / inspect: ALU pipeline activity, SEND activity if exposed, ISA register assignment, controlled register-layout tests. [6] [9]

UNKNOWN Do not map every Pipe stall to XMX. The two platform definitions differ.
06SendResource / dispatch

DOC VTune — Ponte Vecchio [1] [3]

A SEND unit is unavailable to the instruction.

DOC PTI — Arc B-Series [2]

XVE_STALL_SENDWR

At least one thread is waiting for an outgoing SEND message to dispatch while the XVE is stalled.

MODEL Example and mechanism

Port contention, queue pressure or downstream backpressure are plausible mechanisms, not separately identified by the stall counter. A load SEND includes its response destination; no separate RECEIVE instruction is needed.

SEND blocked → request issued → memory response → dependent use

Coalesce and vectorize where appropriate; reduce message count, test working-set size and outstanding depth.

07ControlControl / resource

DOC VTune — Ponte Vecchio [1] [3]

The instruction waits for a branch unit to become available.

DOC PTI — Arc B-Series [2]

XVE_STALL_CONTROL

At least one thread waits for JEU to finish a branch while the XVE is stalled.

MODEL Example and mechanism

Branch processing can affect next instruction address and execution masks. Even uniform loops may contribute.

Branch instruction → JEU → updated control state → next fetch
LOOP:
  dpas ...
  add r10 r10 1
  cmp ... r10 rLimit
  (f0.0) jmpi LOOP

INFERRED Optimization and diagnostic tests

Reduce redundant branches or unroll moderately; compare with instruction-cache and register-pressure costs.

Collect / inspect: Branch instruction count from ISA, fetch stalls, kernel time, occupancy. [6] [9]

UNKNOWN Control stall is not a branch-divergence or misprediction counter.

03 / XMX: a separate matrix engine, not a ninth stall reason

DOC Intel describes XMX (Xe Matrix Extensions) alongside XVE and documents XMX activity and instruction metrics. The standard Ponte Vecchio eight-category stall view has no standalone XMX stall category. [1] [2] [4] [5] [6]

UNKNOWN The cited public material does not identify a universal counter for XMX acceptance backpressure, internal bubbles or queue saturation. Do not assume it maps to Pipe or SBID on every device.

04 / What the counters actually mean

DOC Ponte Vecchio — instruction sampling [3]

Samples attribute an XVE stall to a representative resident thread chosen by Intel's internal heuristic. An XVE stall requires loaded threads and no thread able to execute in the sampled cycle.

Instruction attribution is statistical; it is not a per-thread stall timeline. The source guide reports about 10% expected overhead at its finest interval, not a universal profiler overhead.

DOC Arc B-Series — aggregate counters [2]

Many events qualify when the XVE is stalled and at least one resident thread has the specified condition. Several conditions may qualify in the same cycle.

Do not sum these categories as a mutually exclusive distribution. Check the denominator and metric group for the actual device.

Profiling workflow

1. Measure uninstrumented kernel latency, XVE active/stalled/idle, occupancy and XMX/ALU activity.
2. Check supported stall categories and denominator; use instruction-level samples if the target supports them.
3. Correlate the stalled instruction with its producer, register operands and SWSB dependencies; use Unitrace where supported [10].
4. Form one hypothesis and test it with a controlled change.
5. Re-measure latency and hardware counters. If adding binary trace probes, compare original vs instrumented outputs, ISA, allocation, occupancy and counters. Similar aggregate metrics do not prove identical local timelines.

06 / Hardware-first optimization lab

INFERRED — proposed experiments, not measured results. Begin with the hardware resource, isolate a dependency or a structural hazard, inspect generated ISA, and use supported counters to test the hypothesis. Keep the GPU, compiler, workgroup shape, instruction count and clock conditions fixed where possible; repeat measurements and report occupancy, spills and useful throughput.

MODEL — compute-bound attention load timing

In a Q-stationary attention loop, QK consumes K before PV consumes V. Schedule the K and V loads independently. The next K may be prefetched while current softmax or PV runs; the current V may overlap QK and softmax if register and dependency constraints permit. This is an optimization hypothesis, not a measured Intel schedule.

Load Q and K[0]
for each KV tile i:
    issue load V[i] if buffer available
    QK[i] = Q @ K[i].T       // K must be ready
    issue next K if safe
    P[i] = online_softmax(QK[i])
    wait for V[i] as required
    update output with P[i] @ V[i]

To reuse K/V across multiple Q tiles, distinguish reuse within one hardware thread's private registers from workgroup SLM reuse and cache reuse. Keeping multiple Q tiles and their output accumulators resident increases GRF pressure; evaluate occupancy, spilling and softmax/XMX overlap. The original FlashAttention and FlashAttention-2 papers describe different algorithm loop orders, not universal physical load schedules. See also the public Intel FlexAttention optimization article for register-based implementation trade-offs.

DOC — counter caution: Arc B-Series PTI defines LOAD_STORE_CACHE_INPUT_AVAILABLE as the fraction of time with input present at LSC. It is not a free-slot or accept-ready counter. L3_SUPERQ_FULL explicitly tracks all request slots awaiting return or response. Neither metric alone proves the cause of a SEND stall. See [2].
