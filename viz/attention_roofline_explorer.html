02 Tensor storage dtype

The three presets change Q/K/V storage dtypes only; O always stays BF16. Each MXFP4 element is modeled as 0.5 B data + 1/32 B E8M0 scale metadata. Dtypes affect modeled HBM traffic; set the appropriate TFLOP/s for your QK/PV compute path.

How the model is calculated

Matrix arithmetic (non-causal)

FLOPs = 4 × Hq × N² × d

Ridge point

AI_ridge = GPU_TFLOPs / HBM_TBps

Ideal HBM bytes

N × d × [Hq(sQ + sO) + Hkv(sK + sV)]

Tiled HBM bytes

N × d × [Hq(sQ + sO) + ceil(N/Bq) × (Hq/r)(sK + sV)]

N = shared Q/KV sequence length; d = head dimension; s* = stored bytes per element, including modeled MX scale metadata; r = modeled KV sharing across query heads (1 by default, or Hq/Hkv if enabled). The tiled estimate assumes KV blocks are re-fetched from HBM for each query tile per sharing group; actual L2 reuse can make HBM AI significantly higher. Head dimension cancels from AI in this simplified model but still changes FLOPs, bytes, and predicted time. In practice, GPU utilization, softmax, and on-chip memory effects can reduce achieved performance far below the roof.
